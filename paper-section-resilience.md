## 4.5 Resilience and Observability

CyberVault's infrastructure layer implements a defense-in-depth resilience strategy composed of circuit breakers, retry policies with exponential backoff, structured logging, and Prometheus-compatible metrics. These mechanisms collectively ensure that transient failures in external dependencies — specifically the IPFS decentralized storage network and PostgreSQL database — do not cascade into user-facing outages, and that operators retain full visibility into system behavior under adverse conditions.

### 4.5.1 Circuit Breaker Pattern

The system adopts the circuit breaker pattern \cite{nygard2007release} to prevent cascading failures across service boundaries. The implementation (`src/shared/circuit-breaker.ts`) models three states: **CLOSED** (normal operation), **OPEN** (fault detected, requests rejected), and **HALF_OPEN** (probing for recovery). In the CLOSED state, each failed invocation increments a failure counter. Upon reaching the configurable `failureThreshold` (default: 5 consecutive failures), the circuit transitions to OPEN, causing all subsequent calls to fail immediately without attempting the underlying operation. After a `resetTimeoutMs` interval (default: 30,000 ms), the circuit enters HALF_OPEN, allowing a limited number of probe requests. If `successThreshold` (default: 2) consecutive successes are observed, the circuit returns to CLOSED; otherwise, it reopens.

This state machine is critical for IPFS interactions, where node unavailability can produce prolonged timeouts. Rather than allowing each request to hang for the full duration of a TCP connection timeout, the circuit breaker fails fast after the threshold is reached, returning control to the caller within microseconds. The health check endpoint (`GET /health`) queries the circuit breaker state directly — if the breaker is OPEN, the IPFS dependency is reported as unhealthy without issuing a network probe, avoiding unnecessary load on a degraded node.

### 4.5.2 Retry Strategy with Exponential Backoff

Transient failures — network partitions, temporary IPFS node unavailability, or brief PostgreSQL connection pool exhaustion — are handled by a generic retry utility (`src/shared/retry.ts`). The strategy employs exponential backoff with additive jitter: for attempt $n$, the delay is computed as $\min(\text{baseDelay} \times 2^{n-1}, \text{maxDelay})$, with a jitter factor drawn uniformly from $[0.5, 1.0]$ applied to the computed delay. This jitter distribution reduces thundering-herd effects when multiple clients retry concurrently \cite{google2021sre}.

The retry parameters are tuned per dependency. IPFS operations use `maxAttempts = 3` with a base delay of 100 ms and a maximum delay of 5,000 ms, retrying only on errors matching patterns such as `ECONNREFUSED`, `timeout`, and `fetch failed`. This selective retryability prevents wasting attempts on deterministic errors (e.g., invalid CID format). PostgreSQL read operations use `maxAttempts = 2` to minimize latency amplification for queries, while write operations use `maxAttempts = 3` to maximize durability guarantees. The retry layer composes orthogonally with the circuit breaker — each retry attempt passes through `circuitBreaker.execute()`, ensuring that failures count toward the breaker threshold even during retry sequences.

### 4.5.3 Graceful Degradation

CyberVault distinguishes between **critical** and **optional** dependencies. PostgreSQL, which stores vault metadata and credential records, is treated as critical: if the database is unreachable, the health endpoint returns HTTP 503 (`unhealthy`), and the readiness probe returns `not_ready`, signaling orchestrators to remove the instance from the load balancer. IPFS, by contrast, is optional. When the IPFS node is unreachable or its circuit breaker is open, the `IPFSAdapter` (`src/infrastructure/ipfs/ipfs-adapter.ts`) transparently falls back to an in-memory `Map<string, string>` store. Content is still encrypted before storage and a deterministic CID is derived via the hashing service, preserving the content-addressed interface. The health endpoint reports `degraded` status when IPFS is unavailable, providing operators with visibility without triggering container restarts.

### 4.5.4 Structured Observability

All system events are emitted through a structured JSON logger (`src/shared/logger.ts`) that produces machine-parseable entries containing ISO-8601 timestamps, severity levels (`debug`, `info`, `warn`, `error`), contextual module identifiers, and arbitrary key-value data payloads. In production (`LOG_FORMAT=json`), each log line is a single JSON object, enabling ingestion by log aggregation pipelines (ELK, Loki, CloudWatch) without custom parsers. Log level filtering is configurable via the `LOG_LEVEL` environment variable, with a default minimum of `info`.

Operational metrics are collected by an in-process `MetricsCollector` (`src/shared/metrics.ts`) that exposes a Prometheus-compatible text exposition format at `GET /metrics`. Three metric types are supported: **counters** (monotonically increasing, e.g., `http_requests_total`, `cybervault_vaults_created_total`), **gauges** (point-in-time values, e.g., `active_connections`), and **histograms** (distributions with configurable buckets at [0.01, 0.05, 0.1, 0.25, 0.5, 1, 2.5, 5, 10] seconds, e.g., `http_request_duration_seconds`). Each HTTP request records method, path, and status code labels on the request counter, and request duration in seconds on the histogram, enabling per-endpoint latency analysis and error-rate computation in Grafana or similar dashboards.

### 4.5.5 API-Level Resilience

The HTTP server (`src/infrastructure/api/server.ts`) enforces three additional resilience mechanisms at the request boundary. First, a **request timeout** of 30 seconds is applied via `req.setTimeout()`, after which the connection is destroyed and HTTP 504 (`Gateway Timeout`) is returned if headers have not yet been sent. Second, a **rate limiter** enforces a ceiling of 100 requests per 15-minute sliding window per client IP address, returning HTTP 429 (`Too Many Requests`) when exceeded; a background cleanup interval evicts expired entries every 5 minutes to prevent unbounded memory growth. Third, the **readiness check** (`GET /ready`) verifies that all configured dependencies are reachable before returning HTTP 200, enabling Kubernetes liveness and readiness probes to make informed traffic-routing decisions.

These layers — circuit breakers, retries, degradation, structured logging, metrics, timeouts, and rate limiting — form a coherent resilience architecture that ensures CyberVault remains operational and observable even when individual dependencies experience faults, fulfilling the availability requirements of a credential management system that users depend on for daily authentication workflows.
